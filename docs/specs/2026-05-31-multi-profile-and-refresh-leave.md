# 仕様: マルチプロフィール ＋ リフレッシュ休暇

- 日付: 2026-05-31
- feature key: `multi-profile-and-refresh-leave`
- ステータス: 設計承認済み（実装プランは `docs/plans/2026-05-31-multi-profile-and-refresh-leave.md`）

## 背景 / Why

ukyu は現在、単一ユーザー前提のローカル PWA（Dexie/IndexedDB）。
2 つの不足がある:

1. **複数人を管理できない** — 家族・チームなど複数人の有給を 1 端末で扱いたい。
2. **法定有給以外の休暇を扱えない** — リフレッシュ休暇のような会社独自の休暇は、勤続年数→日数の法定テーブル（`grantRules`）に乗らず、付与日数・更新タイミング・消滅タイミングを手動設定できない。

## 目的 / What

- 1 端末で**複数プロフィールを切り替えて**、それぞれの有給を独立管理できる。
- **リフレッシュ休暇**を、有給とは**完全に別バケツ**の残高として、付与ルール（起点日・周期・日数・消滅）を設定して管理できる。

## ユーザーストーリー

- ユーザーとして、メイン画面上部でプロフィールを切り替え、その人の残高・カレンダー・リストだけを見たい。
- ユーザーとして、設定画面でプロフィールを追加・改名・色設定・並べ替え・削除し、各人の入社日を設定したい。
- ユーザーとして、リフレッシュ休暇のルール（起点日／周期 N ヶ月・年／付与日数）を設定すると、該当日に自動で付与され、未使用分は次回更新で消滅してほしい。
- ユーザーとして、ルールから外れる例外分を手動で 1 件ずつ追加・修正したい（ハイブリッド）。
- ユーザーとして、有給とリフレッシュ休暇の残高を別カードで区別して見たい。色だけでなくラベル・枠線で識別したい（LD 配慮）。

## 決定事項（承認済み設計判断）

| 項目 | 決定 |
|---|---|
| スコープ | 複数人 ＋ リフレッシュ休暇を**一括設計**（`profileId` 軸を最初から入れ、マイグレーション 1 回） |
| 複数人モデル | **1 端末でプロフィール切替**（ログイン無し・クラウド同期なし・ローカルのみ） |
| リフレッシュ休暇の位置づけ | **完全に別バケツ**（有給と独立した残高・消滅、サマリーは別カード） |
| 付与の生成 | **ハイブリッド**（ルールで自動生成＋手動で例外の追加/修正） |
| 更新タイミング | **任意の起点日 ＋ 周期**（N ヶ月 / N 年） |
| 消滅タイミング | **次回更新でリセット**（繰越なし＝use-it-or-lose-it） |
| データ分離方式 | **単一 DB ＋ 全テーブルに `profileId` 列**（別 DB 方式は不採用） |
| 休暇種別の表現 | `Grant` に `leaveKind: 'paid' \| 'refresh'` フラグ（別テーブルにせず Usage 系 UI/ロジックを再利用） |

## 受け入れ基準

1. **プロフィール切替**: メイン画面で切り替えると、残高・カレンダー・予定/履歴がそのプロフィールのデータだけに更新される。
2. **プロフィール管理**: 設定画面で追加・改名・色・並べ替え・削除・入社日設定ができる。最後の 1 件は削除不可（常に 1 プロフィール存在）。
3. **マイグレーション**: 既存（v1）データを持つユーザーが起動すると、既定プロフィール 1 件が自動生成され、既存の grants/usages/settings/grantRules がそれに紐づく。データ欠損ゼロ。
4. **リフレッシュ休暇ルール**: 起点日・周期・日数・有効/無効を設定でき、起点日から周期ごとに Grant が自動生成される。各付与の消滅日 = 次回付与日。
5. **ハイブリッド**: 自動生成分とは別に手動で付与を追加でき、自動生成分を手動修正した場合、再生成で上書きされない。
6. **別バケツ集計**: 有給残高にリフレッシュ休暇は混ざらない。サマリーに別カードが出る。
7. **多重符号化**: リフレッシュ休暇の表示は色だけに依存せず、テキストラベル＋枠線で区別される。
8. **既存テスト**: 既存のテキスト契約（カレンダーの「全予」「午前済」等）は不変。スキーマ変更に伴う fixture 修正は機械的最小限に留める。

## 非機能要件

- **テスト**: 新規ロジック（マイグレーション backfill / リフレッシュ付与生成 / 別バケツ集計）はロジック層に純粋関数として実装し、ユニットテストを付ける（境界＝必須）。
- **非決定要素の DI**: `new Date()`（現在日時）は付与/消滅判定ロジックに直接書かず引数注入する。
- **既存挙動の非破壊**: 単一プロフィール時の見た目・操作は実質変わらない（切替 UI が増えるのみ）。
- **オフライン/ローカル維持**: 認証・サーバ・同期は導入しない（スコープ外）。
- **マイグレーションは 1 回**（Dexie v1 → v2）で完結し、後方互換のロールバックは要求しない。

## スコープ外（YAGNI）

- クラウド同期・認証・複数端末間の共有。
- 管理者がメンバーを横断一覧する「管理者ビュー」（将来の拡張余地としてデータ構造だけ開けておくが、UI は作らない）。
- リフレッシュ休暇以外の追加休暇種別（慶弔・特別休暇など）。`leaveKind` は将来拡張可能にするが今回は `paid` / `refresh` のみ。
- 半休単位の按分など、リフレッシュ休暇特有の複雑な消化ルール（有給と同じ full/am/pm を流用）。
